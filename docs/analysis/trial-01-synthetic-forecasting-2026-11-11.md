# Trial 01: synthetic CPU forecasting comparison

**Recorded:** 2026-11-11
**Evidence class:** synthetic software experiment; not testbed or production research.

## Provenance and setup

This report summarizes the locally ignored outputs under
`experiments/runs/windows-models/trial-01/`. The four forecast jobs used
synthetic fixtures generated by the repository's offline runner. Each fixture
contains 1,800 one-second CPU observations for one synthetic node (30 minutes).
The scenarios were `stable` and `burst`; each used seeds 42 and 43. The four
input database SHA-256 values, in stable-42, stable-43, burst-42, burst-43
order, were `b8f503ff615aeca15fa8d9191d7c8ec1c6f990025fbca83845f316d43bfa73`,
`1b65d6132407f840cd65f3a313a61d70114ef4476b510b7d99669576577a1db8`,
`2faebf908aa831a888d7774f0b2f60e555534d55f11afbc3d0b1548283d9285b`, and
`ac8f9ebec416a567bc2dd5db0c44668c4d7a9d6e79c27bd218674db45095daee`.
These identify generated fixture databases, not external telemetry.

Every run compared `persistence`, `arima`, `ets`, `lstm`, `gru`, `temporal`,
and `transformer` on CPU utilization with a one-second cadence, 60-step
history, horizons 5/10/30/60 seconds, 20 requested epochs, chronological
60/20/20 train/validation/test partitions, and seed 42 or 43. All four runs
completed all seven jobs with no recorded job failures. Each model result
reports 948 training windows, 276 validation windows, and 64 test windows per
horizon. Scores below are test MAE, averaged equally over the four horizons;
lower is better. The average is a compact within-run comparison, not a pooled
estimate across independent datasets.

The recorded software versions were Python 3.11.18, PyTorch 2.6.0+cu126,
statsmodels 0.15.0, and psutil 7.2.2. The reported execution environment was
Linux x86_64 under WSL2 with 16 logical CPUs. The root run configuration
records source commit `61131f394d0444cb087e2370e71d85cbf5a7dc86`; individual
model result records say `git_commit: unavailable` and
`working_tree_dirty: true`. Neural model fit metadata reports CUDA on an
NVIDIA GeForce RTX 3060 Laptop GPU. Here `__cpu` names the forecast target
metric, not the compute device. This was not a controlled GPU benchmark and
does not establish GPU throughput or deployment performance. Recorded model
inference means were measured in this local container and are not live-network
service latency.

## Interpretation and limits

The lowest mean-MAE model changed across all four scenario/seed pairs. The
synthetic stable fixture favored a recurrent or Transformer model, while the
two burst fixtures favored different neural models; persistence won the short
burst horizons. This is useful as an offline runner and metric-path check, not
evidence that any model generalizes to cluster telemetry. The two seeds are
generated variants of two fixed synthetic scenarios, not independent physical
workloads.

All saved interval calibration entries report `insufficient_calibration`
(one calibration example per horizon), and audit coverage is null with only
two audit examples. No calibrated uncertainty or coverage claim is available.
The experiment covers CPU forecasting only; it has no application latency,
request rate, SLO labels, fault trace, energy measurements, policy/simulator
metrics, or physical cluster outcomes.
The synthetic scenario labels are generated labels and should not be
interpreted as observed workload classes. No production candidate selection,
deployment, or actuation decision follows from these results.

The papers listed in the repository's related-work material are architecture
and method guidance only. Distinctions such as permutation-equivariant inputs
or a policy guarded by a safety layer remain design questions here: no such
policy was trained or compared in this forecasting run. This trial does not
reproduce or claim published paper results.
